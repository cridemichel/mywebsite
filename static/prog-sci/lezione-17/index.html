Template negli header e smart pointer

Cristiano De Michele

Argomenti di oggi

  • Template e header: perché un template di classe non si divide fra .hpp e .cpp
  • std::unique_ptr: un oggetto nell’heap con un proprietario che lo distrugge da solo
  • Copiare e cedere: un std::unique_ptr non si copia; la proprietà si cede con std::move
  • La rete con std::unique_ptr: i layer senza un distruttore scritto a mano
  • Cenni a std::shared_ptr: più proprietari per lo stesso oggetto
  • Esercizio: una rete di std::unique_ptr; esercizio facoltativo: un albero binario di ricerca, dal libro

Gli argomenti di oggi nel framework

  • Template e header. Le classi del framework sono template sul tipo dei numeri (Lezione 16), e per questo stanno tutte negli header: layer.hpp, parametricLayer.hpp, sequential.hpp e gli altri, senza un file .cpp per le classi.
  • std::unique_ptr. Sequential tiene i suoi layer in un std::vector<std::unique_ptr<Layer<ntype>>>: la rete possiede i layer e li distrugge quando viene distrutta. I programmi creano i layer con std::make_unique e li consegnano alla rete:
model.add(std::make_unique<DenseLayer<float>>(128, 784));
model.add(std::make_unique<SigmoidLayer<float>>());

Nel Laboratorio 10 anche la vostra Sequential passa da un std::vector di Layer<ntype>* a un std::vector di std::unique_ptr.

Ripasso: header e sorgente

Nella Lezione 08 una classe si poteva scrivere in due modi:

  • divisa in due file: la classe, con i prototipi dei metodi, nell’header .hpp; il codice dei metodi in un file sorgente .cpp, compilato a parte;
  • tutta nell’header, come Eigen e come il framework.

Nella Lezione 16 il template Pesi era tutto in un file. Oggi proviamo a dividerlo in pesi.hpp e pesi.cpp, e vediamo perché per un template non si può.

Ricordate i due passi della Lezione 08:

  1. compilazione: ogni .cpp diventa un file oggetto .o, senza vedere gli altri .cpp;
  2. linking: il linker unisce i file .o e collega ogni chiamata al codice della funzione chiamata. Se quel codice non c’è in nessun .o, si ferma con undefined reference.

Un template diviso in due file

pesi.hpp
#ifndef PESI_HPP
#define PESI_HPP
#include <vector>

template <typename T>
class Pesi {
private:
    std::vector<T> w_;
public:
    Pesi(int Nn, int Ni);
    int quanti() const;
};

#endif
pesi.cpp
#include "pesi.hpp"

template <typename T>
Pesi<T>::Pesi(int Nn, int Ni) : w_(Nn * Ni) {}

template <typename T>
int Pesi<T>::quanti() const { return w_.size(); }

Fuori dalla classe anche ogni metodo è un template: si ripete template <typename T>, e il nome della classe si scrive Pesi<T>.

main_pesi.cpp
#include <iostream>
#include "pesi.hpp"

int main() {
    Pesi<float> f(128, 784);
    std::cout << f.quanti() << " pesi\n";
    return 0;
}

L’errore del linker

pesi.cpp e main_pesi.cpp si compilano senza errori; si ferma il linker:

undefined reference to `Pesi<float>::Pesi(int, int)'
undefined reference to `Pesi<float>::quanti() const'
collect2: error: ld returned 1 exit status

Il codice dei due metodi per T = float non c’è in nessun .o:

  • un template diventa codice macchina solo per un tipo scelto: il compilatore genera la classe e i metodi per ogni tipo usato (Lezione 16), nei file che lo usano;
  • in pesi.cpp il codice dei metodi c’è, ma nessuno usa Pesi<float>: il compilatore non genera niente, e pesi.o è vuoto;
  • in main_pesi.cpp si usa Pesi<float>, ma pesi.hpp ha solo i prototipi: in main_pesi.o restano due chiamate, e il linker non trova il loro codice.

Mancano i metodi, non la classe: sono i metodi a diventare codice macchina.

    Sì, ./build/pesi stampa 100352 pesi: main_pesi.cpp ora vede il codice dei metodi, e il compilatore lo genera per float.

Un template sta tutto nell’header

Un template di classe si scrive tutto nell’header, metodi compresi: chi include l’header vede il codice dei metodi, e il compilatore lo genera per i tipi che usa. I metodi si possono definire dentro la classe, come in Pesi della Lezione 16, o fuori, nell’header, con template <typename T> davanti.

Se più file .cpp usano lo stesso template con lo stesso tipo, il compilatore genera i metodi in ognuno, e il linker ne tiene una copia sola: l’errore multiple definition che si ha definendo la stessa funzione in due file non c’è.

È la scelta del framework, con tutte le classi negli header, e della libreria standard: <vector> è un header che contiene tutto il codice di std::vector. Con g++ 13 il solo bits/stl_vector.h, uno dei file che <vector> include, ha 2135 righe.

Ripasso: il return anticipato

Nella Lezione 08 un’uscita anticipata saltava il delete[]; nella Lezione 09 l’array aveva un proprietario, Buffer, che lo liberava nel suo distruttore a ogni uscita (il RAII). Lo stesso problema, con un oggetto creato con new:

anticipato.cpp
#include <iostream>
#include "layers.hpp"

void costruisci(bool errore) {
    DenseLayer* d = new DenseLayer(128, 784);
    if (errore) {
        std::cerr << "Errore\n";
        return;
    }
    std::cout << d->numero_pesi() << " pesi\n";
    delete d;
}

int main() {
    costruisci(true);
    return 0;
}

Alla riga 8 si esce senza delete: il puntatore d, variabile locale, viene distrutto, ma il DenseLayer resta nell’heap, e nessuno ne conosce più l’indirizzo.

Dopo Errore, l’AddressSanitizer segnala detected memory leaks e Direct leak of 16 byte(s) in 1 object(s): i 16 byte sono il DenseLayer. Su macOS i leak si cercano con leaks (Lezione 08).

Chi fa il delete

In anticipato.cpp il proprietario del DenseLayer è la funzione che lo crea, costruisci, come il main nella Lezione 12: deve farne il delete, e alla riga 8 non lo fa. Un delete d; prima del return basterebbe.

Il proprietario di un oggetto creato con new può essere:

  • una funzione, che ne tiene l’indirizzo in un puntatore: il delete va scritto a mano prima di ogni uscita, ed è facile dimenticarne una, come alla riga 8;
  • un oggetto, con il RAII della Lezione 09: il delete sta nel suo distruttore, che viene chiamato a ogni uscita, e non si scrive più. Sono così Buffer con il suo array e Sequential con i suoi layer.

Il std::unique_ptr della slide seguente è un proprietario del secondo tipo. Con lui il delete non si scrive più, e si riduce il rischio dei due errori della Lezione 08: il leak, un delete dimenticato, e il double free, due delete dello stesso oggetto, che un std::unique_ptr evita perché non si copia.

Un proprietario: std::unique_ptr

Per un oggetto creato nell’heap la libreria standard ha un proprietario già pronto: std::unique_ptr<T>, dall’header <memory> (C++11). È un template di classe che contiene l’indirizzo di un oggetto di tipo T; quando il std::unique_ptr viene distrutto, il suo distruttore fa delete dell’oggetto.

std::unique_ptr<DenseLayer> d = std::make_unique<DenseLayer>(128, 784);
std::cout << d->numero_pesi() << " pesi\n";
  • std::make_unique<DenseLayer>(128, 784) (C++14) crea il DenseLayer nell’heap, come new DenseLayer(128, 784), e restituisce un std::unique_ptr<DenseLayer> che ne contiene l’indirizzo.
  • d si usa come un puntatore, con ->.
  • d è il proprietario del DenseLayer: quando d viene distrutto, per esempio alla fine del blocco in cui è dichiarato, il DenseLayer viene distrutto con lui.

Un return anticipato senza leak

unico.cpp
#include <iostream>
#include <memory>
#include "layers.hpp"

void costruisci(bool errore) {
    std::unique_ptr<DenseLayer> d = std::make_unique<DenseLayer>(128, 784);
    if (errore) {
        std::cerr << "Errore\n";
        return;
    }
    std::cout << d->numero_pesi() << " pesi\n";
}

int main() {
    costruisci(true);
    costruisci(false);
    return 0;
}

Alle righe 9 e 12 d viene distrutto, e il suo distruttore fa delete del DenseLayer: stampa Errore e 100352 pesi, senza leak.

Provate: anticipato e unico

  1. Eseguite anticipato e unico: in quale dei due l’AddressSanitizer segnala un leak? Su macOS l’AddressSanitizer non cerca i leak (Lezione 08): compilate senza e usate leaks, poi lo stesso per unico:

    g++ -std=c++17 -g anticipato.cpp -o anticipato_mac && leaks --atExit -- ./anticipato_mac

    Solo in anticipato. In unico il DenseLayer ha un proprietario, d, che lo distrugge anche quando si esce alla riga 9.

  2. In unico.cpp, dopo la riga 11, scrivete delete d;. Compila?
    No: error: type 'class std::unique_ptr<DenseLayer>' argument given to 'delete', expected pointer. d non è un puntatore ma un oggetto, che contiene un puntatore: il delete lo fa il suo distruttore, e voi non lo scrivete.

Com’è fatto un std::unique_ptr

Una versione ridotta, solo per vedere il meccanismo:

template <typename T>
class unique_ptr {
private:
    T* ptr_;
public:
    unique_ptr(T* p) : ptr_(p) {}
    ~unique_ptr() { delete ptr_; }
    T* operator->() const { return ptr_; }
    T* get() const { return ptr_; }
};
  • ptr_ è l’indirizzo dell’oggetto, e il costruttore lo riceve.
  • Il distruttore fa delete: è la classe Buffer della Lezione 09, scritta una volta per tutti i tipi con un template.
  • L’operatore ->, ridefinito come gli operatori della Lezione 10, e get() restituiscono lo stesso indirizzo, senza cedere l’oggetto: d->numero_pesi() è d.get()->numero_pesi(). Con -> si usa d come un puntatore; get() serve quando si vuole l’indirizzo, per esempio per passarlo a una funzione.

Un std::unique_ptr non si copia

Se un std::unique_ptr si potesse copiare, due oggetti conterrebbero lo stesso indirizzo, e alla loro distruzione farebbero due volte delete della stessa memoria: il double free della Lezione 08. Per questo la copia di un std::unique_ptr è vietata: il suo costruttore di copia e il suo operatore di assegnamento (Lezione 10) sono cancellati con = delete, come nel Singleton della Lezione 13 e in Sequential dal Laboratorio 06:

std::unique_ptr<DenseLayer> a = std::make_unique<DenseLayer>(128, 784);
std::unique_ptr<DenseLayer> b = a;      // non compila: costruttore di copia
std::unique_ptr<DenseLayer> c;          // vuoto, vale nullptr
c = a;                                  // non compila: operatore di assegnamento
error: use of deleted function 'std::unique_ptr<_Tp, _Dp>::unique_ptr(const std::unique_ptr<_Tp, _Dp>&)
       [with _Tp = DenseLayer; _Dp = std::default_delete<DenseLayer>]'

_Tp e _Dp sono i parametri del template std::unique_ptr: il tipo dell’oggetto, DenseLayer, e chi lo distrugge, std::default_delete<DenseLayer>, che fa delete. Un std::unique_ptr non si copia, ma può cedere l’oggetto a un altro std::unique_ptr.

Cedere la proprietà: std::move

cedere.cpp
#include <iostream>
#include <memory>
#include <utility>
#include "layers.hpp"

int main() {
    std::unique_ptr<DenseLayer> a = std::make_unique<DenseLayer>(128, 784);
    std::unique_ptr<DenseLayer> b = std::move(a);
    std::cout << b->numero_pesi() << " pesi\n";
    if (a == nullptr) {
        std::cout << "a non possiede niente\n";
    }
    return 0;
}
  • Riga 8: std::move(a), da <utility>, dice che il contenuto di a si può cedere: b prende l’indirizzo del DenseLayer, e a resta vuoto. Il DenseLayer non viene copiato e non si sposta in memoria: cambia solo il proprietario.
  • Riga 10: dopo la cessione a vale nullptr. Stampa 100352 pesi e a non possiede niente; alla fine solo b fa delete.

Provate: copiare e cedere

  1. In cedere.cpp, alla riga 8, scrivete = a; al posto di = std::move(a);. Compila?
    No: è la copia della slide precedente, use of deleted function.
  2. Rimettete std::move(a), e prima di return 0; scrivete std::cout << a->numero_pesi() << "\n";. Compila? Cosa succede in esecuzione?
    Compila: il compilatore non sa che a è vuoto. Dopo le due righe di output l’AddressSanitizer ferma il programma con SEGV on unknown address 0x000000000008: a contiene nullptr, e numero_pesi legge Nn_ a un indirizzo vicino a 0. Dopo std::move un std::unique_ptr non si usa più.

La rete con std::unique_ptr

Nella Lezione 16 la rete era un std::vector<Layer*>, e i layer andavano distrutti con un ciclo di delete. Scritta come classe, con la copia vietata come nel Laboratorio 06:

class Sequential {
private:
    std::vector<Layer*> layers;
public:
    Sequential() = default;
    Sequential(const Sequential&) = delete;
    Sequential& operator=(const Sequential&) = delete;
    void add(Layer* l) { layers.push_back(l); }
    ~Sequential() { for (Layer* l : layers) delete l; }
};

Con std::unique_ptr, come nel framework:

class Sequential {
private:
    std::vector<std::unique_ptr<Layer>> layers;
public:
    void add(std::unique_ptr<Layer> l) { layers.push_back(std::move(l)); }
};

Che cosa cambia nella rete

  • Niente distruttore. Quando la rete viene distrutta, viene distrutto il suo attributo layers; il std::vector distrugge i suoi std::unique_ptr, e ognuno fa delete del suo layer.

  • Niente = delete. Un std::vector di std::unique_ptr non si copia, e quindi nemmeno la rete: una copia non compila, anche senza = delete.

  • add riceve un std::unique_ptr e lo cede al vettore con std::move. Chi chiama scrive:

    rete.add(std::make_unique<DenseLayer>(128, 784));

    Il risultato di std::make_unique non ha un nome, e si cede senza std::move. Un std::unique_ptr con un nome, invece, si cede con rete.add(std::move(u));, e dopo u vale nullptr.

  • Il distruttore di Layer resta virtual (Lezione 12): il delete di un std::unique_ptr<Layer> passa da un Layer*.

Cenni a std::shared_ptr

std::shared_ptr<T>, sempre da <memory>, permette più proprietari dello stesso oggetto: tiene il conto dei proprietari, che sale a ogni copia e scende quando una copia viene distrutta. L’ultima, quando il conto arriva a 0, fa delete dell’oggetto.

condiviso.cpp
#include <iostream>
#include <memory>
#include "layers.hpp"

int main() {
    std::shared_ptr<DenseLayer> a = std::make_shared<DenseLayer>(128, 784);
    std::shared_ptr<DenseLayer> b = a;
    std::cout << a.use_count() << " proprietari\n";
    return 0;
}

Alla riga 6 std::make_shared crea l’oggetto, come std::make_unique; alla riga 7 il std::shared_ptr si copia, e use_count() stampa 2 proprietari. Nel framework un layer appartiene a una sola rete, e basta std::unique_ptr. std::shared_ptr serve quando non si sa quale dei proprietari verrà distrutto per ultimo: per esempio un layer con i pesi condivisi da due reti.

Soluzione dell’esercizio

esercizio_rete.cpp
#include <iostream>
#include <memory>
#include <utility>
#include <vector>

class Layer {
public:
    virtual ~Layer() { std::cout << "~Layer\n"; }
};

class DenseLayer : public Layer {
private:
    int Nn_, Ni_;
public:
    DenseLayer(int Nn, int Ni) : Nn_(Nn), Ni_(Ni) {}
    ~DenseLayer() override {
        std::cout << "~DenseLayer " << Nn_ << "x" << Ni_ << "\n";
    }
};

Il distruttore di Layer è virtual, e quello di DenseLayer lo ridefinisce, con override (Lezione 12).

Soluzione: il main

esercizio_rete.cpp
int main() {
    std::vector<std::unique_ptr<Layer>> rete;
    rete.push_back(std::make_unique<DenseLayer>(128, 784));
    std::unique_ptr<Layer> u = std::make_unique<DenseLayer>(10, 128);
    rete.push_back(std::move(u));
    std::cout << "fine del main\n";
    return 0;
}
  • Riga 22: il risultato di std::make_unique non ha un nome, e si cede senza std::move.
  • Riga 24: u ha un nome, e si cede con std::move; dopo, u vale nullptr.
  • Righe 22 e 23: std::make_unique<DenseLayer> restituisce un std::unique_ptr<DenseLayer>, che si converte in un std::unique_ptr<Layer>, come un DenseLayer* in un Layer* (l’upcasting della Lezione 15).

Soluzione: cosa stampa

Con g++ su Linux:

fine del main
~DenseLayer 128x784
~Layer
~DenseLayer 10x128
~Layer
  • I layer vengono distrutti dopo l’ultima riga del main, quando viene distrutto rete: il std::vector distrugge i suoi std::unique_ptr, che fanno delete dei layer.
  • Ogni layer stampa prima il distruttore della classe derivata, poi quello della base (Lezione 12).
  • Su macOS, con clang, i due layer escono in ordine inverso: non è un errore, lo standard non fissa quest’ordine.

Senza virtual (punto 3): dopo fine del main compare solo ~Layer, e l’AddressSanitizer si ferma con new-delete-type-mismatch: il delete passa da un Layer* ed esegue solo ~Layer, come nella Lezione 12. Se l’AddressSanitizer non se ne accorge, il programma finisce con due ~Layer e nessun ~DenseLayer. Il distruttore virtual serve anche con std::unique_ptr<Layer>.

Esercizio facoltativo: un albero

Scopo: riscrivere in C++ l’albero binario di ricerca del libro (par. 16.3), con i figli di ogni nodo posseduti da std::unique_ptr, e misurare come cresce la profondità dei nodi con il numero N dei dati (Laboratorio 16.6 del libro).

  • Ogni nodo contiene un dato e ha al più due figli. Un dato nuovo si inserisce partendo dalla radice: se è minore o uguale al dato del nodo si scende a sinistra, altrimenti a destra, fino a un posto libero (Listato 16.5).
  • La profondità di un nodo è il numero di passi dalla radice al nodo; la radice ha profondità 0.
  • Ogni nodo possiede i suoi figli, sinistra e destra, che sono std::unique_ptr<Nodo>. Il puntatore al genitore, su, è un Nodo*, che non possiede niente: se fosse un proprietario, padre e figlio si possiederebbero a vicenda.
  • Distruggere la radice distrugge tutto l’albero, a catena.

Albero: il main

esercizio_albero.cpp
int main() {
    std::mt19937 motore(12345);
    std::uniform_real_distribution<double> uniforme(0.0, 1.0);
    const int R = 100;                                // alberi per ogni N
    for (int N = 100; N <= 10000; N *= 10) {
        double media = 0.0, massima = 0.0;
        for (int r = 0; r < R; r++) {
            std::unique_ptr<Nodo> radice = std::make_unique<Nodo>(uniforme(motore));
            long somma = 0;                           // la radice ha profondita' 0
            int hmax = 0;
            for (int i = 1; i < N; i++) {
                std::unique_ptr<Nodo> nuovo = std::make_unique<Nodo>(uniforme(motore));
                Nodo* p = nuovo.get();                // l'indirizzo, prima di cederlo
                inserisci(std::move(nuovo), radice.get());
                int h = profondita(p);
                somma += h;
                if (h > hmax) hmax = h;
            }
            media += static_cast<double>(somma) / N;
            massima += hmax;
        }                                             // qui radice distrugge l'albero
        std::cout << N << "  " << media / R << "  " << massima / R << "\n";
    }
    return 0;
}

Soluzione dell’esercizio facoltativo

esercizio_albero.cpp
#include <iostream>
#include <memory>
#include <random>
#include <utility>

struct Nodo {
    double dato;
    Nodo* su = nullptr;                      // il genitore: non lo possiede
    std::unique_ptr<Nodo> sinistra, destra;  // i figli: li possiede
    Nodo(double d) : dato(d) {}
};

int profondita(const Nodo* p) {
    int h = 0;
    while (p->su != nullptr) {
        p = p->su;
        h++;
    }
    return h;
}

profondita risale con su fino alla radice, l’unico nodo con su uguale a nullptr.

Soluzione: inserisci

esercizio_albero.cpp
void inserisci(std::unique_ptr<Nodo> nuovo, Nodo* vecchio) {
    if (nuovo->dato <= vecchio->dato) {
        if (vecchio->sinistra == nullptr) {
            nuovo->su = vecchio;
            vecchio->sinistra = std::move(nuovo);
        } else {
            inserisci(std::move(nuovo), vecchio->sinistra.get());
        }
    } else {
        if (vecchio->destra == nullptr) {
            nuovo->su = vecchio;
            vecchio->destra = std::move(nuovo);
        } else {
            inserisci(std::move(nuovo), vecchio->destra.get());
        }
    }
}
  • Righe 24 e 25: nuovo->su = vecchio va scritto prima di std::move(nuovo), perché dopo il nodo appartiene a vecchio->sinistra e nuovo vale nullptr.
  • Riga 27: il nodo nuovo passa con std::move alla chiamata successiva, finché non trova il suo posto; get() dà l’indirizzo del figlio senza cederlo.

Soluzione: i risultati

Nel main, alla riga 37, p conserva l’indirizzo del nodo prima di cederlo: dopo inserisci il nodo appartiene al suo genitore, e p, che non lo possiede, resta valido finché l’albero esiste.

Output:

100  6.5824  12.39
1000  10.9841  21.19
10000  15.715  30.47
  • Da una riga alla seguente N si moltiplica per 10, e la profondità media (seconda colonna) aumenta di 4,4 e poi di 4,7.
  • Se la profondità valesse c ln N più una costante, a ogni riga aumenterebbe di c ln 10 ≈ 2,3 c. Gli aumenti misurati danno c ≈ 2: la profondità media cresce come 2 ln N, molto più lentamente di N.

Soluzione: quanti passi servono

  • Per inserire o cercare un dato si scende dalla radice di un livello a ogni passo: i passi sono tanti quanti la profondità, e crescono anche loro come 2 ln N. Con N = 10 000 sono in media circa 16.
  • Con i dati in ordine crescente ogni nodo finirebbe a destra del precedente: l’albero diventerebbe una catena, di profondità media (N − 1)/2, cioè circa 5000 passi per N = 10 000.
