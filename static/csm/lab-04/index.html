Part 1
Introduction to C++ (part IV)

Where we left off

  • pvector stores NT numbers of type ntype, both fixed once for the whole program at the top of pvector.hpp:

    constexpr int NT=3;     // (it was #define NT 3: why it changed, in Part 5)
using ntype=double;

    A program that needs vectors of double and of float, or in 3 and in 2 dimensions, would need two copies of the class with different names.

  • Generic programming solves this: write the class once, with the type (and the size) as parameters, and let the compiler generate the versions you use: genvec<double>, genvec<float>, … (example N8).

  • The same mechanism lets the compiler compute things before the program runs: template metaprogramming (example N9).

Example N8: genvec.hpp

examples/N8_generic_programming/genvec.hpp

#include<cstdlib>
#include<iostream>
// a generic class (a metaclass or class template)
// ntype can be float, double, long double, ...
constexpr int NT=3;// <---- like #define

template <typename ntype>
class genvec
{
  // private members
  ntype v[NT];

public:

  void set(int i, ntype val)
    {
      v[i] = val;
    }
 
   ntype get(int i) const
    { 
      return v[i];
    }
  void show(void) const
    {
      std::cout << "(";
      for (int i = 0; i < NT; i++) 
        {
          std::cout << get(i);
          if (i < NT-1)
            std::cout << ",";
          else
            std::cout << ")\n";
        }
    }
  genvec()
    {
    }

  ~genvec()
    {
    }
};
  • template <typename ntype> (line 7): genvec is a class template, a recipe for classes. Inside it ntype is a type still to be chosen; the rest is an ordinary class.
  • constexpr int NT=3; (line 5) is a typed constant known when compiling: it can size the array v, like the macro of Lab #1, but it is a real variable with a type and a scope.

Class templates

  • A template is not code yet: it becomes code only when it is used with a given type. So the compiler must see the whole template where it is used: templates are written entirely in the header (.hpp), as we already do for all our classes.

  • A template can have several parameters, also integer ones (non-type parameters), known when compiling:

    template <typename ntype, int NT>     // pmatrixq<double,3>: 3x3 matrices of double (Part 5)
template <class ntype, class engine>  // randnumgen<double,std::mt19937_64> (Part 3)

  • You have already used templates of the standard library: std::initializer_list<ntype> (Lab #2) is one.

  • Each different instantiation is a different class: genvec<double> and genvec<float> are as different as int and double. The cost is paid at compile time; at run time a template class is exactly as fast as the class written by hand.

Example N9: myfibonacci.cpp (1)

examples/N9_metaprogramming/myfibonacci.cpp: the Fibonacci numbers \(F_N = F_{N-1} + F_{N-2}\), computed by the compiler.

#include<iostream>
#include<tuple>
using namespace std;
// FIBONACCI SERIES: F_{n} = F_{n-1} + F_{n-2}
template<int N>
class fib {
public:
static constexpr long int value = fib<N-1>::value + fib<N-2>::value;
// tuple_cat constructs a tuple that is a concatenation of all tuples provided as args. 
// E.g. int a=1;
//      string s="pippo";
//      float f=1.3;
//      auto t=tuple_cat(make_tuple(a), make_tuple(s));
//      auto t2=tuple_cat(t, f);
//      results in the tuple whose elements are:
//      {1, "pippo", 1.3} 
// Note that make_tuple is necessary since this way we convert value to a tuple which can be added to the present tuple
// by tuple_cat. 
static constexpr auto fis = tuple_cat(fib<N-1>::fis, make_tuple(value)); // add value to the tuple
};

// stop recursion
template<>
class fib<1> {
public:
static constexpr long int value = 1;
static constexpr tuple<long int> fis = make_tuple(1);
};

template<>
class fib<0> {
public:
static constexpr long int value = 0;
};

Example N9: myfibonacci.cpp (2)

examples/N9_metaprogramming/myfibonacci.cpp


// type to hold an integer
template<int N> struct int_{static constexpr int n=N;};

template <class T, class I>
void print_tuple(T l, I nel)
{
  cout << get<tuple_size<T>::value-nel.n>(l) << ","; // print n-th element
  int_<nel.n-1> nn;
  print_tuple(l, nn); // recursively print remaining elements
}

// stop recursion
template <class T>
void print_tuple(T l, int_<1>) // we simply provide a type as second argument since istance of second argument is not used  
{
  cout << get<tuple_size<T>::value-1>(l) << "\n";
}
// the following varadic function calls print_tuple where second argument is the number of elements of the tuple
template<class T>
void print_tuple(T l)
{
  print_tuple(l, int_<tuple_size<T>::value>()); // int_<tuple_size<T>::value>() is an object of type struct int_
}
int main()
{
  static constexpr int N = 90;
  fib<N> f;
  cout << "The Fibonacci sequence up to N=" << N << " is:\n"; 
  print_tuple(f.fis);
}

Example N9: how it works

  • template<int N> class fib: one class for each integer N. value is static constexpr: a constant of the class (not of the objects), computed when compiling. fib<N>::value needs fib<N-1>::value and fib<N-2>::value, so the compiler instantiates fib<N-1>, fib<N-2>, …, recursively.
  • template<> class fib<1> and fib<0> are full specializations: for N = 1 and 0 they replace the general template, and stop the recursion, like the base case of a recursive function.
  • fis is a std::tuple, a fixed-size collection of values: tuple_cat appends value to the tuple of fib<N-1>, so fib<N>::fis holds \(F_1, \dots, F_N\).
  • Printing: get<i>(t) needs an index i known when compiling, so a normal for loop cannot be used. print_tuple calls itself with the type int_<n-1>, which carries the index; the overload for int_<1> stops the recursion (function overloading, Lab #2).
  • At run time the program only prints: all the numbers are already in the executable.

In a normal program the overflow would silently give a wrong (negative) number at run time; when the compiler does the computation, the overflow is an error (clang++: constexpr variable 'value' must be initialized by a constant expression).
  • We will not write metaprograms. What we use from this example: constexpr, integer template parameters (template<int N>, the NT of pmatrixq), and the idea that whatever the compiler knows (sizes, constants) costs nothing at run time.

  • Each version is one line, return v[idx];: the non-const one returns a reference to the component (A(1) = 5.0; writes in A), the const one a copy of its value, and it is the one used for const vectors and const pvector& arguments.

Scalar times vector and rint()

project/pvector.hpp

  // scalar times vector 
  // (*this) is not implicitly passed to operator* in this case, 
  // being a friend operator of pvector class
  // pvector A;
  // double s;
  // s*A
  friend pvector operator*(ntype s, const pvector& V2)
    {
      pvector VT;
      for (int i=0; i < NT; i++)
        {
          VT.v[i] = s*V2.v[i];
        }
      return VT;
    }
  // rint() function
  // pvector A, B={1.1,2.2,3.3};
  // A = rint(B);
  friend pvector rint(const pvector& V2)
    {
      pvector VT;
      for (int i=0; i < NT; i++)
        {
          VT.v[i] = rint(V2.v[i]);
        }
      return VT;
    }
  • Both are friend functions, not methods: no *this, all the operands are arguments, and they can read V2.v[i] because they are friends of pvector.
  • In rint, rint(V2.v[i]) has a number as argument: it is the rint() of <cmath>.

Part 3
Random numbers

Random numbers in a simulation

  • Monte Carlo needs many random numbers: to choose a particle and its displacement, to accept or reject the move (compare \(e^{-\beta\Delta U}\) with a number in \([0,1)\)), for initial configurations and velocities: \(10^9\)–\(10^{10}\) in a long run.
  • A computer produces pseudo-random numbers: a deterministic sequence \(X_{n+1} = f(X_n)\), which starts from a seed \(X_0\). Same seed, same sequence: a run can be repeated exactly (useful for debugging); different seeds give independent runs.
  • What we want from a generator:
    • uniformity and no correlations between successive numbers, which must pass statistical tests;
    • a period (length of the sequence before it repeats) much longer than what a simulation uses;
    • speed and a small state (the memory that stores \(X_n\)).
  • Correlated numbers make the simulation sample the wrong distribution, silently.

The simplest generator: linear congruential

  • Fast and with a tiny state, but the period is at most \(m\) (with \(m \leq 2^{32}\): about \(4\times10^9\) numbers, less than a long simulation uses); with \(m = 2^k\) the low bits are poorly random.
  • Consecutive numbers are correlated. Use three of them, \((X_n, X_{n+1}, X_{n+2})/m\), as the position of a point in a cube: the points do not fill the cube, they all lie on a few parallel planes (only 15 for RANDU, an LCG widely used in the 1960s).
  • The C function rand() is often an LCG; in <random> it is std::minstd_rand.

Figure: Wikipedia, “Linear congruential generator”. Planes: G. Marsaglia, PNAS 61, 25 (1968), the same Marsaglia of Part 4.

The generators of the C++ standard library

  • Predictability: from a few outputs one can compute the next ones. It matters in cryptography, not in simulations.
  • State: memory per generator. Period: the Mersenne Twister repeats after \(2^{19937}-1\) numbers, a number with about 6000 digits; ranlux has an excellent period but is very slow.

Table: arvid.io (2018), “On C++ Random Number Generator Quality”.

Statistical tests: PractRand

  • PractRand is a battery of statistical tests applied to more and more output of a generator: 512 MB, 1 GB, …, 2 TB. ✗: the output is detected as not random.
  • LCG (minstd_rand) and the lagged-Fibonacci ranlux*_base fail at once.
  • mt19937 fails at 256 GB, mt19937_64 at 512 GB.
  • ranlux24/ranlux48 pass, but are very slow. Those in bold (splitmix, xorshift, pcg) pass and are fast, but are not in the standard library.

Table: arvid.io (2018), “A Better C++ Pseudo Random Number Generator”.

Why the Mersenne Twister

  • It is in the standard library (std::mt19937, std::mt19937_64 in <random>): no external code to install.
  • Statistically good enough for us: a long MC run uses \(\sim 4\times10^{9}\) numbers of 64 bits, i.e. \(\sim 32\) GB of output, well below the 512 GB where mt19937_64 starts to fail the most demanding tests.
  • A huge period (\(2^{19937}-1\)), and an acceptable speed: in a simulation most of the time goes into the energies, not into the random numbers.
  • A good compromise between quality, speed and availability. Its weaknesses (predictability, a state of a few KB, the failure after hundreds of GB) do not matter for our simulations.

The class randnumgen (1)

project/randnumgen.hpp (complete: you do not have to change it)

#ifndef _RANDNUMGEN_
#define _RANDNUMGEN_
#include<chrono>
#include<random>
// use by default mersenne-twister rng engine
template <class ntype, class engine>
class randnumgen {
  std::random_device rd;
  using myclock = std::chrono::high_resolution_clock;
  engine rng;
  using ud = std::uniform_real_distribution<ntype>;
  // we use a pointer here since if a range different from [0,1) is needed
  // we can use the constructor of uniform_real_distribution class 
  // to provide a different range (see randnumgen()) 
  // If a different range is not needed, the default constructor can be used
  // and one can avoid to use a pointer to uniform_real_distribution class
  ud* unidst;
public:
  // fixed seed
  void seed(int s)
    {
      std::seed_seq seq{s+1, s+2, s+2};
      rng.seed(seq);
    }
  // random seed
  void rseed(void)
    {
      // int operator()() {}
      // ticks since 1/1/1970
      unsigned int t=myclock::now().time_since_epoch().count(); 
      // ^ is bitwise XOR
      std::seed_seq seq{rd()^t,rd()^t, rd()^t};
      rng.seed(seq);
    }

How to use randnumgen

rng.seed(1);        // fixed seed: the same sequence at every run
rng.rseed();        // or: a different seed at every run (clock + std::random_device)
double xi = rng.ranf();   // uniform in [0,1)
  • randnumgen is a class template (Part 1) with two type parameters: the number type (double) and the engine (std::mt19937_64, the 64-bit Mersenne Twister). The engine produces random integers; std::uniform_real_distribution turns them into numbers in \([0,1)\).
  • Line 59 defines one global object rng: every file that includes randnumgen.hpp (pvector.hpp now does, line 39) uses the same generator, hence one sequence for the whole program. This works because our programs have a single .cpp file.
  • unidst: created with new in the constructor, freed with delete in the destructor (N6).
  • Without seed() or rseed() the engine starts from its default seed: every run gives the same numbers. Seed once, at the beginning of main, never inside a loop.
  • The standard does not fix the algorithm of the distributions: with the same seed, another compiler may give other numbers. Only the statistics must agree.

random(L): a random vector in a box

  • Each component uniform in \([-L/2, L/2)\): rng.ranf() is uniform in \([0,1)\), so (rng.ranf()-0.5)*L is uniform in \([-L/2, L/2)\).
  • Why centred in the origin: it is the box of the minimum image convention (Lab #3), dr - L*rint(dr/L) has components in \([-L/2, L/2]\). The same recipe gives the random displacement of a Monte Carlo move, \(\delta\,(\xi-0.5)\) for each component.
  • A check: for \(x\) uniform in \([-L/2, L/2)\), \(\langle x\rangle = 0\) and \(\langle x^2\rangle = L^2/12\).

Spherical coordinates fail

  • Goal: \(\hat{\mathbf{u}}\) uniform on the sphere: the probability of a region \(\propto\) its area (solid angle).
  • The naive way: \(\theta\) uniform in \([0,\pi]\), \(\phi\) uniform in \([0,2\pi)\), and \(\hat{\mathbf{u}} = (\sin\theta\cos\phi, \sin\theta\sin\phi, \cos\theta)\). Wrong.
  • Think of the grid of meridians and parallels: uniform \(\theta\) and \(\phi\) put the same number of points in each cell \(\Delta\theta\,\Delta\phi\), but the cells shrink near the poles, where the meridians converge: a higher probability at the poles.
  • In formulas, the area of a cell, which vanishes at the poles, is \[d\Omega = \sin\theta\, d\theta\, d\phi\]
  • In numbers: the cap \(z > 1/2\) (\(\theta < \pi/3\)) is 1/4 of the sphere, but the naive method puts there 1/3 of the points.
  • The right distribution: \(d\Omega = d(\cos\theta)\, d\phi\) (up to the sign), so \(z = \cos\theta\) must be uniform in \([-1,1]\) (not \(\theta\)), and \(\phi\) uniform in \([0,2\pi)\).

Wrong and right

  • 4000 points each. Left: \(\theta\) and \(\phi\) uniform: the points crowd at the poles (the centre of the top view, the top and bottom of the side view). Right: Marsaglia’s algorithm: the same density everywhere.
  • See also “Sphere Point Picking” on Wolfram MathWorld.

Marsaglia’s algorithm

  1. Take \(V_1, V_2\) uniform in \((-1, 1)\) and compute \(S = V_1^2 + V_2^2\).
  2. If \(S \geq 1\) reject the pair and go back to 1: the accepted \((V_1,V_2)\) are uniform inside the unit circle (probability of acceptance \(\pi/4 \simeq 0.785\)).
  3. The unit vector is \[\hat{\mathbf{u}} = \left(2V_1\sqrt{1-S},\; 2V_2\sqrt{1-S},\; 1-2S\right)\]

Why it works: \(S\) is uniform in \((0,1)\) and independent of the direction \((V_1, V_2)/\sqrt{S}\), so \(z = 1-2S\) is uniform in \((-1,1)\) and \((x, y) = \sqrt{1-z^2}\,(V_1,V_2)/\sqrt{S} = 2\sqrt{1-S}\,(V_1,V_2)\) has a uniform random direction.

  • Only two random numbers per try and one square root: no sin, cos, acos.
  • Detailed proof: “Detailed proof of Marsaglia’s algorithm”, PDF on the course page (Lectures → Lab notes). Original paper: G. Marsaglia, Ann. Math. Statist. 43, 645 (1972).

random_orient(): implementation

  • A do { ... } while (S >= 1.0); loop for steps 1–2, with rng.ranf(): 2.0*rng.ranf()-1.0 is uniform in \([-1,1)\).
  • Then set the components, e.g. with the constructor with initializer_list and operator=: (*this) = {..., ..., ...};, or one by one with v[0], v[1], v[2].
  • The algorithm is for 3D vectors: if NT is not 3, print a message.
  • Checks (the goal pvector.cpp does them): the norm is 1 up to rounding errors (\(\sim10^{-16}\)); \(\langle z\rangle = 0\), \(\langle z^2\rangle = 1/3\) (as for \(x\) and \(y\), since \(x^2+y^2+z^2=1\)); the fraction with \(z > 1/2\) is \(1/4\).

The goal: pvector.cpp

#include "./pvector.hpp"
int main(void)
{
  rng.seed(1);                // fixed seed: the same random numbers at every run
  const int M = 1000000;      // number of random vectors
  const ntype L = 10.0;       // side of the box
  pvector R, U;

  // random(L): each component uniform in [-L/2, L/2)
  ntype rmin = L, rmax = -L, x2 = 0;
  for (int k = 0; k < M; k++)
    {
      R.random(L);
      for (int i = 0; i < NT; i++)
        {
          if (R(i) < rmin) rmin = R(i);
          if (R(i) > rmax) rmax = R(i);
        }
      x2 += R(0)*R(0);
    }
  std::cout << "random(L): min=" << rmin << " max=" << rmax
            << " <x^2>=" << x2/M << " (exact L^2/12=" << L*L/12 << ")\n";

  // random_orient(): uniform on the unit sphere
  ntype dnmax = 0, z = 0, z2 = 0, cap = 0;
  for (int k = 0; k < M; k++)
    {
      U.random_orient();
      ntype dn = fabs(U.norm() - 1.0);
      if (dn > dnmax) dnmax = dn;
      z  += U(2);
      z2 += U(2)*U(2);
      if (U(2) > 0.5) cap++;  // spherical cap z > 1/2: a quarter of the sphere
    }
  std::cout << "random_orient(): max|norm-1|=" << dnmax << "\n"
            << "  <z>=" << z/M << " (exact 0)  <z^2>=" << z2/M << " (exact 1/3)"
            << "  P(z>1/2)=" << cap/M << " (exact 1/4)\n";
  return 0;
}

Why NT is now constexpr

pmatrix.hpp includes pvector.hpp (it will need vectors for matrix times vector). With the macro of Lab #1, #define NT 3, it does not compile:

pvector.hpp:41:12: error: expected '>' before numeric constant
pmatrix.hpp:25:31: note: in expansion of macro 'NT'
  • The preprocessor replaces every NT with 3, also the template parameter: template <typename ntype, int 3> is not C++. A macro has no type and no scope (Lab #1).
  • With constexpr int NT=3; (pvector.hpp, lines 40–43) the global constant and the template parameter NT of pmatrixq can coexist: inside the class the parameter hides the global name. The same happens for ntype.

Classic pitfalls

  • Seeding inside a loop: with rng.seed(1) before each ranf() you get always the same number; with rseed() each number comes from a new seed, and the statistical properties of the Mersenne Twister sequence are lost. Seed once, at the beginning of main.
  • No seed at all: every run gives the same numbers (the default seed). Fine for debugging, wrong for independent runs.
  • Spherical coordinates with \(\theta\) uniform: points crowd at the poles. Also normalizing a random vector of the cube \([-1,1)^3\) is not uniform (the directions of the corners are favoured), unless the points outside the unit sphere are rejected first.
  • Forgetting the rejection in Marsaglia’s algorithm: the pairs \((V_1,V_2)\) must be uniform inside the circle, not in the square.
  • A template used without its arguments: pmatrixq M; does not compile, write pmatrixq<double,3> M;.
  • m[k/NT][k%NT] with a list longer than \(NT^2\): writes outside the matrix.
